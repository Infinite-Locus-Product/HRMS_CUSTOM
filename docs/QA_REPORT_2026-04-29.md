## 3. Open findings — consolidated punch list

### 3.1 Medium severity (3)

| ID | Surface | Description | Source |
|---|---|---|---|
| **F-PA-6** | HR Policy | `applicability_logic="AND"` only ANDs *contributing* filter tables — a single populated table makes AND visually identical to OR. **Documented as intentional**; would be a breaking change to flip. Decision needed: keep current behavior or normalize to "AND across populated *and* empty tables". | [HR_POLICY.md:324](HR_POLICY.md#L324) |
| **F-4** | Employee Action Centre | `HR Policy.acknowledgement_required` (default 1) is read by no code path. Actual check-in gate is `mandatory_check_in_block`. Misleading to HR users editing policies. **Fix:** delete the field via patch + JSON edit, or wire it to gate child-row creation in `_ensure_policy_rows`. | [EMPLOYEE_ACTION_CENTRE.md:201](EMPLOYEE_ACTION_CENTRE.md#L201) |
| **HOL-7** | Holiday | 0/10 demo employees have `holiday_list` set. Optional-leave validation throws when unset. **Fix:** either default `Employee.holiday_list` from company default on insert, or surface a clear error in the leave form ("Ask HR to assign you a holiday list"). | [HOLIDAY.md:87](HOLIDAY.md#L87) |

### 3.2 Low / open (18)

Grouped by surface so they can be batched per-PR.

**Employee Action Centre**
- **F-10** — re-share on `Employee.user_id` reassignment isn't wired (EMPLOYEE_ACTION_CENTRE.md:207).
- **F-13** — no Reject UI for policies in PWA (PA Phase 2 scope says this is intentional, can close).

**Employee Checkin**
- **F-5** — naming drift: `custom_bypass_geolocation_check` / `validate_distance_from_shift_location` / "geofence" — pick one term (EMPLOYEE_CHECKIN.md:205).
- **F-6** — bypass is total today (no lat/long captured). Product call: "skip radius only" vs "skip everything" (EMPLOYEE_CHECKIN.md:206).

**Leave & Attendance**
- **LA-AR-bulk** — no HR-side bulk-approve action on Attendance Request (LEAVE_AND_ATTENDANCE.md:451). Mirror the pattern from the existing `bulk_approve_leave_applications` endpoint.

**HR Policy**
- **F-PA-7** — version bump on file change uses URL-equality, no content hash. Re-uploading the same physical file under a new URL still bumps the version (HR_POLICY.md:325).

**Permissions**
- **PERM-1** — User Permission shows direct reports only, not sub-tree descendants. CEO sees VPs but not their reports' reports (EMPLOYEE_PERMISSIONS.md:154). Standard Frappe limitation; may need a custom recursive permission query.

**Setup & patches**
- **SET-3** — option-merge pattern for existing field options is in `_ensure_holiday_type_options` only; not generalized. Refactor into a setup helper.
- **SET-4** — `yarn build` runs every migrate (5–10s overhead) even when Vue unchanged. Add a content-hash skip.
- **SET-5** — no introspection for `after_migrate` work; reading code is the only way to know what runs. Consider a `bench --site X execute myhr.setup.describe` helper.

**Whitelist hardening (input validation)**
- **SEV-2-1** — `acknowledge_policy_acknowledgement(name)` accepts dict/list (not type-validated as string).
- **SEV-2-2** — `bulk_approve_leave_applications(names)` has no row-count cap; could submit thousands per call.
- **SEV-2-3** — `update_action_centre_field` doesn't validate `fieldname` exists on the doctype (HR can write any string key).
- **SEV-2-4** — `reupload_document(file_url)` doesn't sanity-check the URL scheme.
- **SEV-3-1** — `get_employee_directory()` has no per-record permission gate. **Intentional** (it's the contact book by design) but worth re-confirming with the user.
- **SEV-3-2** — `get_optional_leave_types()` is globally readable; over-exposed for what is essentially a PWA dropdown helper.

> **Important correction to a prior agent observation:** the QA_REPORT_WHITELIST_AUDIT.md flagged `get_leave_coverage`, `get_checkin_coverage`, `get_attendance_request_coverage`, and `get_action_centre_coverage` as missing role gates. **Verified in code:** all four have explicit `frappe.get_roles()` checks at the top of the function body (api.py:665, api.py:730, api.py:785, api.py:905). No security hole.

## 4. Design-system compliance (DESIGN_SYSTEM.md §11)

DESIGN_SYSTEM.md just landed (2026-04-28). Pre-existing components have not been retrofitted yet. Concrete violations across `frontend_changes/`:

### 4.1 By severity

| # | Anti-pattern | Hits | Severity |
|---|---|---|---|
| 1 | `<Button variant="solid">` (clashes with brand blue) | 8 | High — visible mismatch |
| 2 | Native `<input type="date">` (native browser calendar) | 2 | High — UX regression vs DatePicker |
| 3 | Solid red buttons with `theme="red" variant="solid"` | 8 | Med — should be rose-tint outline |
| 4 | Off-brand blue (`bg-blue-500`, `bg-blue-700`) for primary | 4 | Low — mostly chart legend dots, semantics differ |
| 5 | Hand-rolled status pills instead of `<Badge>` | ~18 | Low — visually consistent, but defers theming away from frappe-ui |

### 4.2 File:line for the high-priority hits

**Stock `<Button variant="solid">` to convert** (8 — confirmation dialogs + action sheets):
- `components/FormView.vue:251` — Delete confirm dialog
- `components/FormView.vue:283` — Submit confirm dialog
- `components/FormView.vue:314` — Cancel confirm dialog
- `components/RequestActionSheet.vue:329`, `:368`, `:389`, `:471`, `:512`

**Native `<input type="date">` to convert** (2 — both in EAC's employer slots):
- `views/EmployeeActionCentre.vue:339` — `employer_*_from`
- `views/EmployeeActionCentre.vue:353` — `employer_*_till`

These two are the most impactful to fix because the rest of the app's Date fields (LA, AR, expense) already use the popover DatePicker — opening an EAC employer card and getting the OS date picker is the most jarring UX miss right now.

### 4.3 Fix path

All eight Button cases sit inside frappe-ui `<Dialog>` confirmation footers. Per [DESIGN_SYSTEM.md §8.3](DESIGN_SYSTEM.md#83-confirmation-dialog) the canonical pattern is "secondary (gray) + primary (blue)" — replace `<Button variant="solid">` with the native blue button class string from §4.1. Estimated 30 min for all eight.

The two native date inputs need either (a) wrapping in `<FormField fieldtype="Date">` so they get the patched DatePicker, or (b) inlining the frappe-ui `<DatePicker>` directly. Estimated 20 min for both. **Recommended priority: fix this in the next session** — it's small, visible, and the design-system doc explicitly forbids it.
